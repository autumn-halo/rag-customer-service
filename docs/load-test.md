# 压测报告：100 用户并发场景

> 工具：Locust 2.47 · 环境：Docker 部署（单容器，与生产一致）· 数据：14 篇知识文档、100 个压测用户
> 测试日期：2026-10-22 · 原始数据：`docs/loadtest-results/*.csv`

## 一、测试场景设计

| 场景 | 内容 | API 消耗 | 目的 |
|---|---|---|---|
| A | 登录 + 会话列表浏览 | 零 | 基础承载、数据库并发读 |
| B | 聊天-答案缓存命中（预热 5 个问题） | 零 | 系统自身吞吐上限 |
| C | 聊天-真实大模型（100 人各问 1 个不重复问题） | 真实 | 端到端体验、首字延迟 |

每个场景 100 并发用户（20 用户/秒爬坡）。自定义流式指标：
`chat_ttfb`（首个字延迟）、`chat_total`（完整回答耗时）。

## 二、最终结果（修复后）

### 场景 A：登录 + 浏览（2 分钟）

| 指标 | 中位数 | P95 | 最大 | 失败 |
|---|---|---|---|---|
| 登录 | 350ms | 530ms | 540ms | 0 |
| 会话列表 | 10ms | 38ms | 58ms | 0 |

100 人同时在线平稳运行，数据库读取毫无压力。

### 场景 B：缓存命中聊天（3 分钟，802 次问答）

| 指标 | 中位数 | P95 | 失败 |
|---|---|---|---|
| 聊天接口（响应头） | 11ms | 860ms | 0 |
| **首字延迟 chat_ttfb** | **540ms** | 2.0s | 0 |

吞吐 9.5 请求/秒，802 次流式问答零失败。

### 场景 C：真实大模型问答（100 人各 1 个独特问题）

| 指标 | 中位数 | P95 | 最大 | 失败 |
|---|---|---|---|---|
| **首字延迟 chat_ttfb** | **1.3s** | 1.7s | 2.0s | 0 |

100 人同时真实问答（含检索 + 重排 + 大模型），所有人 2 秒内看到第一个字，**零失败**。

## 三、压测发现的两个真实瓶颈（及修复）

### 瓶颈 1：登录限流在压测中"误触发"（机制验证 ✅）

- **现象**：首轮场景 A 中 275/280 次登录被 429 拒绝
- **原因**：防暴力破解限流（5 次/分/IP）正常工作——压测用户全部来自本机同一 IP，触发了保护
- **结论**：安全机制真实生效（生产环境用户 IP 各异不受影响）
- **处理**：压测用 `docker-compose.loadtest.yml` 覆盖放宽（生产配置不动）

### 瓶颈 2：数据库连接池耗尽 ⚠️（真实缺陷，已修复）

- **现象**：场景 B 中登录耗时 118 秒、36% 失败；聊天 60~119 秒、大量 500
- **根因**：`QueuePool limit of size 5 overflow 10` 连接池打爆。流式问答期间
  数据库会话全程持有连接（每个 20~30 秒的长流占 1~2 条），100 并发远超默认 15 条容量
- **修复**：
  1. 聊天服务重构为**短会话模式**：仅在会话创建/引用快照/落库三个阶段开短会话，
     流式生成期间**零连接占用**
  2. 流式接口鉴权改用短会话依赖（原 yield 依赖会随流持有连接）
  3. 连接池扩容 20+40、超时收紧到 10 秒
- **复测**：场景 B 从"53 请求/53% 失败"变为"**1704 请求/0 失败**"；登录恢复 1.5 秒中位数

## 四、顺带发现的成本问题：重排免费额度耗尽

场景 C 第二轮压测中，qwen3-rerank 接口开始返回 403：
`AllocationQuota.FreeTierOnly: Free quota exhausted`（约 1000+ 次调用后）。

- **优雅降级实证** ✅：重排失败后系统自动回退到 RRF 排序，聊天未中断（0 个 500）
- **代价**：每次失败重试 3 次（指数退避约 7 秒），首字延迟升至 23 秒
- **启示**：生产环境需监控第三方 API 额度/余额，并对持续失败**熔断**（跳过重试快速降级）

## 五、优化建议（按性价比排序）

1. **缓存前置**（省 API 调用）：当前缓存查询在检索之后，缓存命中仍要调重排 API。
   改为"问题 + 知识库版本号"做缓存键 → 命中直接返回，跳过检索与重排
2. **重排熔断**：连续 N 次 403/429 后暂停调用一段时间，直接走降级路径（避免 7 秒重试拖慢全部请求）
3. **登录限流自适应**：内网/办公网场景按 IP 段放宽，或对已登录用户豁免（当前实现已足够毕设场景）
4. **SQLite 写入权衡**：Docker 共享目录不支持 WAL（写操作串行化）。写入密集场景可改
   Docker named volume（原生文件系统可开 WAL），或升级 MySQL
5. **bcrypt 登录峰值**：100 人同时登录时中位数 350ms~1.5s（CPU 密集）。大流量场景
   可在网关层做登录排队或换 argon2id

## 六、复现方法

```bash
# 1. 压测环境（放宽限流）
docker compose -f docker-compose.yml -f docker-compose.loadtest.yml up -d

# 2. 准备数据（幂等）
cd backend
.venv/Scripts/python ../scripts/loadtest/prepare_users.py
.venv/Scripts/python ../scripts/loadtest/warm_cache.py

# 3. 运行场景（A/B/C 分别跑）
PYTHONUTF8=1 .venv/Scripts/python -m locust -f ../scripts/loadtest/locustfile.py \
    --host http://localhost:8000 --users 100 --spawn-rate 20 \
    --tags scenario_b --run-time 3m --headless --only-summary \
    --csv ../docs/loadtest-results/b
```

## 七、结论

**100 用户并发下系统表现达标**：登录/浏览无压力；缓存命中问答首字延迟 0.5 秒；
真实大模型问答首字延迟 1.3 秒（P95 1.7 秒）；全程零失败。
压测同时暴露并修复了连接池缺陷，验证了限流与优雅降级机制的真实有效性——
这正是压测的价值：**用数据发现问题，用架构修复问题**。
