# 面试速查：高频技术问题与答题要点

> 结合本项目（RAG 电商知识库问答系统）的真实实现准备，每个问题先给一句话结论，再给展开要点。

## 1. 什么是 RAG？为什么需要它？

**一句话**：RAG（检索增强生成）就是"开卷考试"——先从知识库检索相关资料，再把资料连同问题交给大模型作答，解决大模型"知识过时、幻觉编造、无法溯源"三个问题。

**展开**：普通对话模型凭参数记忆回答，电商政策随时变、商品数据千差万别，闭卷必错；RAG 把答案约束在检索到的资料上，还能给出引用出处，这是企业客服场景的底线要求。

## 2. 你的检索是怎么做的？为什么不用纯向量检索？

**一句话**：向量 + BM25 双路粗选 → RRF 融合 → 重排模型复试，三级的"漏斗"。

**展开**：
- 向量检索擅长语义相近（"怎么退"→"退货流程"），但商品型号、专有名词这类精确词容易漏；
- BM25 关键词检索恰好互补：精确词必中；
- 两路分数体系不同（余弦相似度 vs 词频统计），不能直接相加，用 RRF（只比较名次）融合；
- 最后用 qwen3-rerank 精排，把最相关的片段喂给模型，引用质量决定回答质量。

## 3. 怎么防止大模型瞎编（幻觉）？

**三层防线**：
1. **提示词约束**：强制"只依据参考资料作答、禁止编造、必须标注 [n] 引用"；
2. **兜底阈值**：重排最高分低于 0.15（或无资料）直接返回固定话术，**根本不调用大模型**；
3. **意图分流**：闲聊问题走自由对话，商品问题才走严格模式，避免一刀切。

## 4. 流式回答（SSE）是怎么实现的？

**一句话**：EventSource 不支持 POST，前端用 `fetch + ReadableStream` 手动解析事件流。

**展开**：自定义事件协议 `meta → delta×N → done/error`；meta 先携带引用信息（引用面板先于答案渲染）；服务端每 15 秒发心跳注释防超时断连；nginx 反代必须 `proxy_buffering off` 否则流会被攒住一次性返回；用户可随时中断（AbortController）。任何异常都转成 error 事件，流不会 500。

## 5. 多用户、多会话、历史记录怎么设计的？

- 5 张表：users / conversations / messages / documents / chunks；
- 会话按 user_id 隔离，接口层校验归属（他人会话返回 404，不泄露存在性）；
- **引用快照存进消息表**：历史消息重渲染无需再查库，删除文档后历史回答仍完整——这是"快照 vs 引用"的取舍点；
- 会话标题自动取首问前 20 字；列表按更新时间倒序（复合索引）。

## 6. 系统怎么处理性能与并发？

- **异步入库**：上传立即返回，解析/向量化走 asyncio 队列 + 线程池（阻塞操作不卡事件循环），状态轮询；
- **答案缓存**：LRU+TTL 内存缓存，键绑定"问题+引用片段集合"（知识库变了缓存自动失效），相同问题秒回且省 API 费用；
- **限流**：滑动窗口限流器，登录 5 次/分/IP 防爆破、提问 20 次/分/用户防刷；
- 批量向量化（每批 25 条 + 指数退避重试）、SQLite WAL、路由懒加载。

## 7. 为什么用 SQLite / Chroma，不用 MySQL / Milvus？

**一句话**：单机可跑原则——毕业设计/中小企业场景部署成本优先，但换的成本被我压到了最低。

**展开**：数据库用 SQLAlchemy 抽象（换 MySQL 只改环境变量）；检索层实现 LangChain BaseRetriever 接口（语料超 10 万块换 Chroma server 或 Qdrant 不动业务代码）；缓存、重排、任务队列同理都是接口隔离。**"先轻量后企业级、接口预留替换路径"比直接上重组件更能体现工程判断**。

## 8. 遇到过的坑（最有价值的面试题）

1. **阿里云已下架 gte-rerank** → 官方推荐 qwen3-rerank，且它与对话/向量化走不同的 API 通道（compatible-api vs compatible-mode）；
2. **新版 langchain-openai 默认把文字预分词成 token 编号发送**，DashScope 兼容模式只收原文 → 读源码定位，找到官方参数 `check_embedding_ctx_length=False` 关闭（官方文档写明是给非 OpenAI 厂商用的）；
3. **Python 3.14 与 chromadb 不兼容**（onnxruntime 无 wheel、pypika 用了已移除的 ast.Str）→ 调研后锁 3.12，写进 README 设计决策记录；
4. **Windows bat 中文乱码吞换行**（GBK 编码问题）→ 纯英文脚本根治。

## 9. 如果知识库有 100 万篇文档，哪里会先撑不住？怎么扩？

- **内存 BM25 全量重建**先撑不住 → 换增量索引或外部检索引擎（Elasticsearch）；
- Chroma 嵌入式单进程 → server 模式 / Qdrant（接口已抽象）；
- 单进程入库队列 → Celery + 消息队列（任务抽象已隔离在 queue.py）；
- 内存缓存 → Redis（CacheBackend 接口已预留）；
- 大模型 API 限流 → 多 Key 池 + 更细的限流调度。
顺序很重要：**先量数据，再扩瓶颈，不要提前过度设计**。

## 10. 你做的项目最满意的设计是什么？

（个人化回答建议）**意图分流 + 三层防幻觉**：商品问题严格引用、查不到老实说不知道；闲聊问题自然对话。用最小的成本（40 个关键词）换来了体验和底线兼得，并且整个 RAG 链路的每一环（解析/分块/双路检索/RRF/重排/兜底/缓存）都有独立单元测试和假实现，91 个测试全程零 API 消耗——"每一环都可测、可替换"是工程化最得意的地方。

## 附：答辩/演示路径（30 分钟）

1. 启动（start.bat 或 docker compose up）→ 登录页 → admin 登录；
2. 知识库管理：上传 PDF/Excel 各一个 → 状态流转（2 秒轮询）→ 分块预览；
3. 问答演示：退货政策（带 [1] 引用 + 右侧面板）→ 商品参数（耳机续航）→ 无关问题（兜底不瞎编）→ "你是什么大模型"（意图分流）；
4. 多会话：新建会话、重命名、刷新恢复历史；注册普通用户 → 看不到管理入口 → 调管理接口 403；
5. 工程展示：README 架构图、91 测试、93% 覆盖率、docker compose 一条命令部署。
